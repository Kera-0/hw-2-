# ДЗ 2. Генерация кода

Архив весов `checkpoint_130m.zip` доступен в [релизе v1.0](https://github.com/Kera-0/hw-2-/releases/tag/v1.0). Он размещён отдельно из-за ограничения GitHub на размер файлов. Остальные файлы находятся в репозитории.

## 1. Данные и модель


Итоговая модель — Transformer с энкодером и декодером, похожий на BART: 130 183 936 параметров, 6 слоёв энкодера, 3 слоя декодера, размер скрытого состояния 1024, 16 голов внимания, FFN 3840 и dropout 0,1. Короткий декодер выбран для ускорения генерации. Токенизатор — byte-level BPE со словарём 8192 токена, обученный на первых 50 тысячах обучающих пар; он сохраняет пробелы и отступы.

Около 2% вопросов выделены для валидации по хешу нормализованного текста. Одинаковые после нормализации вопросы не попадают одновременно в обучение и проверку. Для сравнения моделей использовались одни и те же 1024 вопроса. Это не исключает похожие по смыслу задачи.

Для итогового обучения взяты все 60 частей train. После исключения валидационных групп и слишком длинных пар осталось 11 549 805 примеров. Лимиты: 192 токена на вопрос и 256 на программу. Исходные ответы не переписывались.

## 2. Как проходило обучение

1. Базовая модель 77M. Обучил на 978 505 примерах за 10 000 шагов. При лимите генерации 64 токена бот показал public pass@1 48,65%: 467 из 960 задач. Часть программ обрывалась: 692 из 1919 тестовых генераций не дошли до конца.
2. Увеличение длины ответа. На той же модели проверил лимиты 64, 128, 192 и 256 токенов. Локальная точность выросла с 46,90% до 57,58%, 57,99% и 58,09%. Значит, слишком короткий лимит заметно ухудшал результат.
3. Модель 130M. Обучил с нуля на 5 873 423 примерах за 40 000 шагов. Лучшим оказался шаг 38 000: локально 685 из 983 задач, или 69,68%. Обучение заняло около 63 минут на H100 без подготовки данных.
4. Продолжение 130M V2. Взял собственный checkpoint шага 38 000, расширил данные с 30 до 60 частей train и обучал ещё 60 000 шагов. Это заняло около 100 минут на H100. Лучший результат получен после 50 000 дополнительных шагов: 697 из 983, или 70,91%. На последнем шаге было 694 правильных ответа, поэтому для сдачи выбран лучший checkpoint. Прирост к первой 130M — 12 задач, или 1,22 процентного пункта.

Обе версии 130M обучались на H100 80GB: BF16, AdamW, weight decay 0,01, batch 128 с накоплением градиентов за 2 шага и seed 42. В первом запуске learning rate был 0,0003 с разогревом 1000 шагов; в V2 — 0,00008 с разогревом 500 шагов. Дальше learning rate снижался по косинусу. Токенизированные данные сохранялись в Arrow, батчи группировались по длине.

В V2 одновременно изменены объём данных, learning rate и число шагов. Их отдельный вклад я не измерял.

## 3. Проверка качества и скорости

Локальная проверка сравнивает численные результаты программ через ограниченный AST-интерпретатор. Он поддерживает 983 эталона из 1024. Поэтому приведённые локальные проценты не равны официальному pass@1 бота. У выбранной V2 validation loss — 0,2698, точность предсказания токенов — 91,68%.

Для финального выбора длины генерации получились такие результаты:

| Лимит токенов | Первая 130M | 130M V2 |
| --- | --- | --- |
| 128 | 682/983 — 69,38% | 692/983 — 70,40% |
| 192 | 685/983 — 69,68% | 697/983 — 70,91% |
| 256 | 685/983 — 69,68% | 697/983 — 70,91% |

Выбрал 192 токена: увеличение до 256 не улучшило точность. Для ускорения используются FP16, генерация без перебора вариантов, кеш внимания и batch 128. Вопросы сортируются по длине, затем исходный порядок ответов восстанавливается.

На H100 генерация 1919 программ заняла 3,31 секунды без загрузки модели. Шесть программ не достигли токена конца. Вопросы взяты из официального `test.parquet`; отдельная сверка порядка с файлом бота не выполнялась.

В сохранённых материалах нет замера на настоящей T4 и официального результата V2 от бота. Лимит 180 секунд пока не подтверждён. Ноутбук для T4 измеряет запуск нового процесса целиком: импорты, распаковку, загрузку модели, токенизацию, генерацию и запись ответов. Установка пакетов и загрузка входных файлов выполняются заранее.

## 4. Как использовался ИИ-агент(o3 agent наш ко)

ИИ-агент помог разобрать условие, написать код обучения и проверки, организовать запуски на H100, найти проблему с обрывом программ. С его помощью добавлены Arrow-кеш, логи экспериментов, сохранение лучшей модели и отдельный замер полного запуска на T4. Это помогло сравнивать варианты по сохранённым результатам и выбирать длину генерации. Дополнительные обучающие ответы с помощью агента не создавались.

## 5. Что находится в папке

| Файл | Содержимое |
| --- | --- |
| `code_submission.zip` | Код обучения, подготовки данных, проверки и генерации; история экспериментов и логи |
| `checkpoint_130m.zip` | Итоговые веса 130M V2, токенизатор и настройки |
| `inference_t4.ipynb` | Ноутбук генерации и замера на T4 в Colab |
| `inference_kaggle_t4.ipynb` | Ноутбук генерации и замера на T4 в Kaggle |
| `questions_used.jsonl` | 1919 тестовых вопросов в использованном порядке |
| `submission_130m.jsonl` | 1919 сгенерированных программ для отправки боту |
| `README` | Сохранённый отчёт |

Код самого обучения есть в `code_submission.zip`:

- `code/train_new.py` — продолжение обучения итоговой 130M V2;
- `code/train_h100.ipynb` — ноутбук запуска продолжения на H100;
- `code/hw2_core.py` — модель, токенизатор и общие функции;
- `code/data_and_export.py` — подготовка данных и сохранение ответов;
- `code/history/first_130m/train_130m.py` — обучение первой 130M с нуля;
- `code/history/baseline_77m/` — код и ноутбук базовой модели;
- `code/artifacts/` — параметры, метрики и результаты экспериментов.

Для повторения продолжения обучения нужен checkpoint первой 130M и восстановленная валидационная выборка. Родительский checkpoint в эту папку не включён: по описанию архива он сохранён отдельно в `hw2_130m_final.zip`. Для генерации ответов итоговой моделью он не требуется.

## 6. Как запустить на T4 и сдать

1. Загрузить `inference_t4.ipynb` в Google Colab и выбрать T4 GPU.
2. Загрузить рядом `checkpoint_130m.zip` и `questions_used.jsonl`.
3. Выполнить все ячейки. Проверить `rows=1919`, `actual_t4=true`, `t4_limit_verified=true` и `cold_subprocess_seconds <= 180`. При нехватке памяти поставить `BATCH_SIZE=64` и повторить замер.

## 7. Проверка на T4 через Kaggle

1. Открыть [Kaggle Code](https://www.kaggle.com/code) → New Notebook. Через File → Import Notebook загрузить `inference_kaggle_t4.ipynb` из этой папки.
2. В настройках выбрать Accelerator → GPU T4 x2 и включить Internet для установки пакетов. Ноутбук использует только первую T4 через `CUDA_VISIBLE_DEVICES=0`, вторая в вычислениях не участвует.
3. Через Add Input / Add Data создать приватный Dataset и загрузить два файла: `checkpoint_130m.zip` и `questions_used.jsonl`. Добавить этот Dataset к ноутбуку. Код сам найдёт файлы в `/kaggle/input`. Если Kaggle распакует ZIP, ноутбук соберёт его обратно перед замером. Архив с кодом для этого запуска не нужен.
4. Нажать Run All. Дождаться окончания установки пакетов и генерации. Подготовка файлов и установка пакетов выполняются до таймера; замер включает новый Python-процесс, распаковку архива, загрузку модели и генерацию всех ответов.
5. Проверить итоговый вывод:

   ```text
   rows: 1919
   parameters: 130183936
   actual_t4: true
   t4_limit_verified: true
   cold_subprocess_seconds: не больше 180
   ```

   Если возникла ошибка нехватки памяти CUDA, изменить `BATCH_SIZE = 128` на `BATCH_SIZE = 64` в ячейке запуска и повторить замер. Если время больше 180 секунд, требование домашки не выполнено, даже если файл ответов создан.
6. В последней ячейке скачать `submission_130m.jsonl` и `submission_130m.timing.json`. Они также находятся в `/kaggle/working`. Отправить полученный JSONL боту, а время из timing-файла добавить в отчёт.
7. Сохранить выполненную версию: Save Version → Save & Run All. После завершения скачать notebook с результатами ячеек и сохранить оба выходных файла из этой версии.
